# Astron 竞赛视频脚本

> 版本边界：本材料依据历史证据基线 `11c6114f6ec0504628f912ebde9ba53821badb03`；只支持该基线对应的陈述，不构成 ZIP 中 `d32d3ec1bc49a78d0b14aabb6bf0daf79d3f4d88` 快照的运行或测试证据。详见同目录 README。


**目标时长：**约 4–5 分钟<br>
**叙事顺序：**问题 → 洞察 → 架构 → 真实实跑 → 意义<br>
**主要比较对象：**通用 Tool-Calling Agent

## 0:00–0:30 — 问题

**画面：**用简洁动画展示模型提出工具动作，动作进入真实工作区。随后依次出现三个问题：“允许执行吗？”“动作实际发生了吗？”“任务真的完成了吗？”画面保持清爽，不滚动终端输出。

**旁白：**

“能调用工具的 Agent 可以完成实际工作，但模型的一句回答，无法单独证明某个动作是否获得授权、是否已经生效，也无法证明用户要求的结果是否有效。遇到超时或进程中断，动作结果可能变得不确定。模型说‘我完成了’，也不等于任务已经通过核验。”

## 0:30–1:00 — Astron 的洞察

**画面：**逐行呈现英文架构口号：*The model proposes. The runtime decides. The verifier accepts.* 随后用中文标注对应关系：模型提出动作、运行时决定是否执行、Verifier 验收任务。

**旁白：**

“Astron 是面向通用 Tool-Calling Agent 的执行治理运行时。它把模型提出的动作转化为经过授权、留下耐久记录、并由独立 Verifier 核验的执行过程。模型可以建议下一步；可信运行时检查身份、权限和范围，记录动作事实；是否完成，则由 Verifier 根据预先声明的条件决定。”

## 1:00–2:15 — 真实成功实跑

**画面：**展示 `ASTRON_REAL_MODEL_END_TO_END_PROOF_V1` 的证据卡片：任务约束、五次模型决策、五次工具动作、代码变更、交付物和摘要核对。用计数器或固定图卡，不展示终端滚屏。

**旁白：**

“接下来是 Astron 的真实模型端到端成功实跑。任务范围很明确：把受控仓库中的 `MAX_RPS` 从 10 改为 20，保留另外两个常量，并交付一份报告。

“这次任务记录了五次真实 Provider 调用、五次模型决策和五个工具动作提议。五个动作都经过授权、实际执行，并写入动作日志：三次读取、一次精确补丁，以及一次报告写入。应用记录和执行前后工作区快照没有观察到禁止变更或范围外写入；这不是操作系统级的完整写入审计。

“交付物确实生成了。系统记录的 SHA-256 与我们从交付物重新计算出的摘要一致。这些证据连在一起，展示了一个受控任务从模型提出动作，到运行时治理执行，再到交付物核对的完整正向链路。

“启动配置请求的模型标识是 `deepseek-flash`。不过，Provider 返回的模型字段没有被耐久记录，所以我们不能据此确认服务端实际报告了哪个模型。”

## 2:15–3:00 — Verifier 控制任务完成

**画面：**用清晰时间线展示：`PROPOSE_COMPLETE` → `VERIFICATION_STARTED` → 两项条件通过 → `VERIFICATION_ACCEPTED` → `TASK_SUCCEEDED`。突出模型提出完成和任务最终成功之间的核验步骤。

**旁白：**

“模型提出完成之后，任务还没有成功。Astron 随后核验了两项事先声明的条件：速率上限确实提高，报告也确实交付。两项条件都通过后，Verifier 接受结果；耐久记录写入接受状态，任务才进入 `TASK_SUCCEEDED`。

“这就是我们希望评委记住的一句话：AI 说完成，不等于任务真的完成。”

## 3:00–3:45 — 面向动作事实的恢复

**画面：**全程标注“独立的运行时与确定性故障注入证据”。示意 `ATTEMPT_STARTED` 后进程中断且没有可信终态，状态变为 `UNCERTAIN`；再展示“基于可信外部事实核对”。只有确认动作未生效后，才显示“可申请重试”，并注明仍需显式调用。不要使用本次成功实跑的画面暗示恢复发生在其中。

**旁白：**

“恢复能力由留存故障矩阵摘要和运行时测试支持，范围限于已测故障窗口；原始逐进程输出目录目前不在本机，无法在本次审查中逐条复查或重放。这是另一组独立证据，并没有发生在刚才那次成功的真实模型实跑中。在已测试的崩溃和结果不确定窗口里，Astron 会先持久化动作尝试。如果进程中断时还没有可信的最终结果，动作就进入 `UNCERTAIN`，而不是因为没有收到回复就直接重做。

“运行时需要依据可信外部事实核对动作。如果证据确认动作没有生效，才可以进入允许重试的状态；之后仍然需要一次明确调用。这样，恢复依据是动作真实进行到了哪一步，而不是只恢复聊天记录或模型计划。”

## 3:45–4:20 — 架构与证据

**画面：**展示一张简明流程图：Agent / 模型 → 动作提议 → 可信身份与权限检查 → 有界工具运行时和耐久动作日志 → 交付物 → Verifier → 接受完成。旁注：“Checkpoint 是一种记录；恢复还要结合动作日志与核对结果。”

**旁白：**

“这套架构把智能和执行权威分开。Planner、Memory、RAG 和 Skills 可以为模型提供上下文、帮助形成提议，但它们本身不授予权限。运行时依据可信身份和范围决定动作能否执行，并记录尝试及结果。Verifier 检查交付物和验收条件，再决定能否耐久地接受完成。每项结论都只适用于对应的证据等级和已测试场景。”

## 4:20–5:00 — 意义与边界

**画面：**回到片头的三个问题，并分别以“授权记录”“动作日志与核对”“Verifier 验收”作答。最后展示一张简短的证据边界卡，再以项目定位和记忆点收尾。

**旁白：**

“对开源开发者来说，执行过程能否被检查很重要：我们需要知道动作为什么获准、实际尝试了什么、哪些结果仍不确定，以及任务为什么被接受。Astron 聚焦的是通用 Tool-Calling Agent 执行过程中的这些责任；它不声称其他框架没有类似机制。

“这份证据有明确边界：真实模型成功实跑只有一个受控任务；恢复证据来自独立的故障测试及留存摘要，原始逐进程输出不可复查；留存测试日志也不是当前提交的新鲜全量测试收据。我们没有与通用 Agent 做公平对照，也没有统计可靠性估计。现有证据不能证明生产可靠性、任意外部系统的 exactly-once，也不能确认 Provider 实际报告的模型身份。

“模型提出动作，运行时决定，Verifier 验收。AI 说完成，不等于任务真的完成。”
